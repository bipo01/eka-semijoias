# ÉKA Semijoias — project guide

The real website of **ÉKA Semijoias** (Brazilian semi-fine jewelry, owner Érika; pre-production with stand-in photos). Sales close over WhatsApp; the catalog is managed by Érika from her phone in the admin at `/admin` and stored on the server, so every edit reaches every visitor (live, over WebSocket).

Live: https://eka-semijoias.eka-semijoias.workers.dev/ (clean URLs, e.g. `/catalogo`, `/admin`; Cloudflare account subdomain `eka-semijoias`; D1 database `eka-semijoias`, region ENAM).

Hosting: **one Cloudflare Worker** (`wrangler.jsonc`) serves the built SPA (Workers Static Assets), the JSON API (`/api/*`), uploaded photos (`/media/*`) and the live WebSocket (`/api/live`). Data in **D1**; live fan-out in a **Durable Object**; photos in **R2** when the `MEDIA` binding exists, otherwise in D1 (current state: R2 is not enabled on the account, so photos are in D1; to switch, enable R2 in the dashboard, `npx wrangler r2 bucket create eka-semijoias-media`, add `"r2_buckets": [{ "binding": "MEDIA", "bucket_name": "eka-semijoias-media" }]` to `wrangler.jsonc` and redeploy; new uploads go to R2 and existing ones keep being served from D1). The old GitHub Pages address (https://bipo01.github.io/eka-semijoias/) only forwards to the Cloudflare site. Backend design and decisions: `docs/backend/PLAN.md` (prompts: `docs/backend/PLANNING_PROMPT.md`, `docs/backend/IMPLEMENTATION_PROMPT.md`).

CI (`.github/workflows/deploy.yml`): `npm ci` → typecheck → lint → unit → worker unit → integration → build; on `main` it also publishes the GitHub Pages forwarding page (`deploy/github-pages/index.html`). Cloudflare deploys are manual (`npm run deploy`). E2E is not in CI; run it locally before pushing UI changes.

## Structure
- `src/config/business.ts` — unconfirmed business facts (`null` hides the claim) + the admin checklist. Settings saved in the admin override contact fields and warranty (`src/hooks/useBusiness.ts`).
- `worker/` — the Cloudflare Worker: `index.ts` (routing, document CSP, request logs), `http.ts` (error shape `{error:{code,message,details}}`, body limits, same-Origin guard), `db.ts` (D1 retry + `guard()` compare-and-swap), `auth.ts` (PIN login, sessions, throttling), `catalog.ts` (snapshot reads, first-run seeding, change sets; re-materializes the stock map and drops orphan stock rows), `orders.ts` (public `POST /api/orders`; admin list, status changes that move stock, anonymize, delete), `payments.ts` (admin Pix charge → payment link token; public `GET /api/pay/:token` and receipt upload; admin-only receipt download), `stock.ts` (admin stock read/write, snapshot publishing), `conflicts.ts`, `media.ts`, `leads.ts`, `live.ts` (`LiveHub` Durable Object), `migrations/` (D1 schema), `test/` (unit + integration).
- `src/data/` — `schema.ts` (zod schemas/types, `SCHEMA_VERSION` 2, `Catalog` = public catalog incl. optional `stock` map and `settings.pix`/`settings.lowStockThreshold`, `CatalogState` = backup with leads), `stock.ts` (stock rules shared by both sides), `orders.ts` (order schemas, statuses/transitions, server pricing `priceOrder`), `report.ts` (sales report, computed in the browser), `seed.ts` (24-product initial catalog; the server seeds D1 from it on its first request), `integrity.ts` (backup migrations, `checkIntegrity`, `validateCatalog`; shared with the Worker), `changes.ts` (change sets: diff/apply/chunk; shared), `storage.ts` (localStorage helpers for per-visitor data + catalog cache + legacy-catalog detection), `catalog.ts` (selectors: prices, badges, variant galleries).
- **Catalog data flow:** `GET /api/catalog` returns a materialized snapshot (ETag `"c<version>"`, 304 on revalidation; `/api/catalog/v/<n>` is immutable and edge-cached). The browser keeps the last snapshot in `eka:catalog-cache:v2` and renders it instantly on return visits; `CatalogGate` holds pages until the first catalog is known (never a flash of "não encontrado"). Admin edits: `save(update)` → `commit` diffs the catalog, uploads new photos (data URLs → `POST /api/admin/media`, content-addressed keys `media/<sha256>.<ext>`), sends one change set with `baseVersion` and an `Idempotency-Key`, and only updates state after the server confirms. The server checks per-entity conflicts (incl. tombstones for deleted items), integrity and photo existence, then commits rows + snapshot in one D1 batch guarded by the catalog version; then the `LiveHub` pushes `{type:"catalog",version}` to every open page.
- **Orders and stock:** the bag's "Finalizar pedido" registers the order (`POST /api/orders`, `Idempotency-Key` per bag content; the server prices it from the snapshot and refuses sold-out/over-stock lines with 409), then shows the number and the "Enviar pedido pelo WhatsApp" link (no Pix at checkout); on a network failure it offers WhatsApp without a number.
- **Message templates:** every WhatsApp text comes from `src/data/messages.ts` (12 types: 6 the customer sends from site buttons, 6 the owner sends from the admin; 3–4 built-in variations each, "Clássica" = the original wording). `settings.messages` stores only the owner's changes (active variation, edited built-in texts, her own variations), validated strictly on write; reads fall back to the defaults when it does not validate. Rules: `{variavel}`, optional `[ … ]`, lines whose variables are all empty disappear, values are never altered by the tidy-up. Site: `useMessages()`; admin: Painel → Mensagens (editor with live preview) and "Enviar mensagem" in an order (`OrderMessages.tsx`). Plan: `docs/vendas/MENSAGENS_PLAN.md`.
- **Payment:** in the admin order, "Cobrar por Pix" confirms the order if needed (stock held) and creates `order.charge` (items + frete − desconto) with a secret token (`orders.pay_token`); a new amount issues a new token. The owner copies the ready WhatsApp message (link `/pagamento/<token>` + Pix copia e cola). The payment page (`src/pages/Payment.tsx`, lazy, outside the store layout) shows the summary, QR/copia e cola and takes receipts (PNG/JPEG/WebP/PDF; big images become JPEG in the browser, `src/lib/receipt.ts`; server sniffs magic bytes; ≤ 1.9 MB, 6 per order, D1 `receipts` table). Receipts are personal/financial data: admin-only (`/api/admin/receipts/:id`), erased by anonymize/delete. The admin sees a "Comprovante" badge and accepts with "Pagamento conferido" (→ pago). Brand illustrations: `assets/illustrations/` (generated in ChatGPT) → `npm`-less `node scripts/prepare-illustrations.mjs` → `public/images/illustrations/`. Stock truth is `stock_tracked` + `stock_levels` (a tracked product's missing combination counts as 0); every stock change rewrites the snapshot's `stock` map (capped at 20) and bumps the catalog version in the same guarded batch. Statuses: enviado → confirmado → pago → entregue, or cancelado (`src/data/orders.ts`); entering confirmado/pago/entregue takes tracked items out of stock, leaving gives back exactly `order.stockMoves`. History in `stock_movements`. Orders (personal data) are admin-only; the live channel only says `{"type":"orders"}` to admin sockets.
- `src/store/` — Zustand stores: `catalog` (server catalog, `status`, `version`, async `commit` queue, live connection via `startCatalog()`, `leadsVersion`/`ordersVersion`), `cart`, `checkout` (the order just registered, in memory), `favorites`, `customer`, `ui` (toasts, panels, open-dialog count).
- `src/lib/` — `api` (fetch wrapper, `ApiError` with pt-BR messages), `live` (WebSocket client: heartbeat, backoff, reconnect on focus/online), `pix` (static Pix BR Code + CRC16, key validation), `orders` (order API client), `pin` (PIN policy shared with the Worker), `format` (BRL), `whatsapp` (order message + `wa.me` links), `catalogQuery` (URL-driven filters), `lead` (reseller form schema/mask, shared with the Worker), `search`, `slug`, `assets` (public asset/srcset helpers), `image` (photo pipeline), `csv`.
- `src/components/{ui,layout,product,home,bag}`, `src/pages/*`.
- `src/admin/` (lazy route chunk at `/admin`, opens on Pedidos): `PinGate` (6–8 digit PIN checked by the server), `AdminApp` (session check, returns to the keypad when a request finds the session expired), `AdminShell` (tabs Pedidos · Produtos · Estoque · Relatório · Mensagens · Categorias · Revendedoras · Configurações · Backup, open-order badge, connection banner), `sections/OrdersPage` (status flow, cancel, anonymize, delete), `sections/StockPage` (per-product stock with compare-and-swap, movements), `sections/ReportPage` (periods, KPIs, chart, rankings, stale orders, CSV), `products/` (list, full-screen form with photo manager and variants editor, `productDraft.ts` validation), `sections/` (categories, leads from the API + CSV, settings + Pix + "últimas unidades" threshold + PIN change + checklist, backup: server export, import/restore as change sets, offer for a legacy localStorage catalog), `lib/` (async `save()`, session API, leads hook, contact formatting, downloads, reorder).
- localStorage keys: `eka:catalog-cache:v2` (offline copy of the catalog), `eka:cart:v1`, `eka:favorites:v1`, `eka:customer:v1`. `eka:catalog:v1` is the pre-backend catalog; the admin Backup page offers to download it or send it to the site.

## Backend operations
- **Secrets** (Worker secrets, never in the repo): `PIN_PEPPER` (≥ 32 random chars; keys the PIN and IP hashes; rotating it invalidates the stored PIN) and `ADMIN_INITIAL_PIN` (accepted only until a PIN is stored; the first login stores it). Set with `npx wrangler secret put <NAME>`.
- **Admin access**: PIN of 6–8 digits; 5 attempts per network per 15 min (then 15 min → … → 24 h locks), 50 per hour globally (devices that logged in before are exempt from the global cap). Sessions: `__Host-eka_admin` cookie (HttpOnly, Secure, SameSite=Strict), 14 days idle / 30 days max; changing the PIN ends the other sessions.
- **Locked out or forgot the PIN**: `npx wrangler d1 execute eka-semijoias --remote --command "DELETE FROM throttle"` clears locks; `... --command "DELETE FROM admin_credentials"` makes `ADMIN_INITIAL_PIN` valid again (set a new one with `wrangler secret put` first).
- **Schema changes**: add `worker/migrations/NNNN_name.sql`; `npm run deploy` applies pending migrations before deploying. Never edit an applied migration.
- **Rollback**: `npx wrangler rollback` (code). D1 Time Travel restores the database to a point in time (`npx wrangler d1 time-travel restore`), 7 days on the Free plan, whole database (leads included).
- **Receipts:** `POST /api/pay/:token/receipt` is throttled to 20/hour per network and 300/hour overall. Receipts live in D1 (rows ≤ 2 MB).
- **Orders:** `POST /api/orders` is throttled to 15/hour per network and 300/hour overall; a test order can be deleted in the admin (only while it holds no stock: cancel first). Production test orders must be deleted right after.
- **Free plan limits** that matter: 100k Worker requests/day (static assets are free and unmetered), 10 ms CPU per request, D1 5 GB / 5 M rows read per day. Upgrade (Workers Paid) before traffic nears the request cap or before adding orders/Pix.

## Ground rules
- UI copy in Brazilian Portuguese; code, comments and commits in English.
- Voice: this is the real site, not a demo. No "demonstração/prévia/exemplo/placeholder/ilustrativa/não é segurança/pendente" in the public UI. The brand speaks as itself ("a gente", "nós"); never mention Érika in the third person (her name only on Sobre, in first person). `e2e/public.spec.ts` enforces this on every public route.
- Stack: Vite 8 + React 18 + TypeScript strict + Tailwind v4 (tokens as CSS variables in `src/styles/tokens.css`, mapped with `@theme inline`; custom utilities via `@utility` so responsive variants work) + `createBrowserRouter` with clean paths (`/catalogo`, `/produto/<slug>`, `/admin`; the Worker answers every page route with `index.html`, see `run_worker_first` in `wrangler.jsonc`; old `#/` links are rewritten by `src/legacyHashRedirect.ts`), Vite `base: '/'`. Static files at the root must be listed as `!/<file>` in `run_worker_first` so they skip the Worker.
- Unconfirmed business facts live only in `src/config/business.ts`. Never hard-code them elsewhere, never present them as confirmed.
- Design tokens: exact hex values and contrast results in `docs/PLAN.md` §1.1. Rose gold `#B48C78` is never text on light backgrounds; copper `#8A5A45` is the primary/action color. WhatsApp actions use copper, never WhatsApp green.
- Sheets/drawers/modals use the native `<dialog>` wrapper `src/components/ui/Sheet.tsx` (focus trap, Esc, focus return). Toasts portal into the topmost open dialog because modal dialogs make the rest of the page inert.
- Images: seed images are asset stems (`images/products/<name>` → `-480.webp`/`-960.webp`; wide lifestyle shots also `-1440`); uploads are content-addressed server photos (`media/<sha256>.<webp|jpg|png>`, main ≤ 1200 px + 480 px `thumb`), served immutable from `/media/`; data URLs exist only in the admin until the save uploads them. Stand-ins are tracked with `placeholder: true` in data only.
- Never use the reference brand's (Áthama) name, photos or copy.
- Money is integer centavos; format with `formatBRL` (`Intl.NumberFormat('pt-BR', { style: 'currency', currency: 'BRL' })`).
- Storage and API writes must surface errors; never fail silently, never show an unconfirmed save as saved.
- Every server write is validated with the shared zod schemas and `checkIntegrity`; the browser runs the same checks first for instant feedback, but the server is the authority.
- Personal data (leads) only through admin endpoints; never in the public snapshot, logs or WebSocket messages.
- Seed content to replace before go-live (the seed only fills an empty database; after that, edit through the admin): testimonials (`src/content/home.ts`), the Sobre story (`src/pages/About.tsx`), stand-in photos.

## Tools
