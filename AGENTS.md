# ÉKA Semijoias — project guide

The real website of **ÉKA Semijoias** (Brazilian semi-fine jewelry, owner Érika; pre-production with stand-in photos). Sales close over WhatsApp; the catalog is managed by Érika from her phone in the admin at `/admin` and stored on the server, so every edit reaches every visitor (live, over WebSocket).

Live: https://eka-semijoias.eka-semijoias.workers.dev/ (clean URLs, e.g. `/catalogo`, `/admin`; Cloudflare account subdomain `eka-semijoias`; D1 database `eka-semijoias`, region ENAM).

Hosting: **one Cloudflare Worker** (`wrangler.jsonc`) serves the built SPA (Workers Static Assets), the JSON API (`/api/*`), uploaded photos (`/media/*`) and the live WebSocket (`/api/live`). Data in **D1**; live fan-out in a **Durable Object**; photos in **R2** when the `MEDIA` binding exists, otherwise in D1 (current state: R2 is not enabled on the account, so photos are in D1; to switch, enable R2 in the dashboard, `npx wrangler r2 bucket create eka-semijoias-media`, add `"r2_buckets": [{ "binding": "MEDIA", "bucket_name": "eka-semijoias-media" }]` to `wrangler.jsonc` and redeploy; new uploads go to R2 and existing ones keep being served from D1). The old GitHub Pages address (https://bipo01.github.io/eka-semijoias/) only forwards to the Cloudflare site. Backend design and decisions: `docs/backend/PLAN.md` (prompts: `docs/backend/PLANNING_PROMPT.md`, `docs/backend/IMPLEMENTATION_PROMPT.md`).

## Structure
- `src/config/business.ts` — starting business facts (`null` hides the claim) + the admin checklist. Settings saved in the admin override contact fields and warranty; Configurações → "O que a loja oferece" (content section `loja`) overrides antialérgicas, envio, parcelamento, banho, consignado and investimento (`src/hooks/useBusiness.ts`, `factsOf` in `src/content/defaults.ts`).
- **Site content (Painel → Site, docs/conteudo/PLAN.md):** `src/data/content.ts` defines 12 sections (`inicio`, `depoimentos`, `perguntas`, `sobre`, `cuidados`, `garantia`, `revendedoras`, `contato`, `geral`, `privacidade`, `compartilhar`, `loja`) with zod limits; each is a catalog entity (change kind `content`, id = section) validated by the schema of its id. Stored in `app_config` rows `site:<id>` = `{version, content|null}` (a restore keeps the row with `null`, so a stale save from another device is a conflict) and published in the snapshot as `catalog.content` (only edited sections; `snapshotBody()` carries it through every stock/order/kit rewrite). The site renders `useSection(id)` (`src/hooks/useSection.ts`): the saved section or the built-in text of `src/content/defaults.ts`, which depends on the confirmed facts and never claims an unconfirmed one. A section the client cannot read falls back to the built-in text (never breaks the catalog); `validateCatalog` refuses it before a save. Content photos go through the same upload (wide profile, 1600 px, for banners) and server existence check as product photos, and travel in backups. Testimonials start empty and require the customer's authorization. Admin: `src/admin/sections/site/*` (cards, per-section editor with counters, list editor, image field, restore, conflict dialog) and `LojaSettings.tsx`.
- **Share tags:** `worker/seo.ts` + `serveDocument` (HTMLRewriter) write `<title>`, description, `og:*`, `twitter:*`, canonical and `noindex` (admin, revenda, pagamento, /r/) per page from the snapshot: the `compartilhar` section by default, a product link shows the piece (name, price, photo). One snapshot read per document load; any failure keeps the built-in tags. The built-in hero preload stays only on `/` with the built-in hero picture.
- `worker/` — the Cloudflare Worker: `index.ts` (routing, document CSP, request logs), `http.ts` (error shape `{error:{code,message,details}}`, body limits, same-Origin guard), `db.ts` (D1 retry + `guard()` compare-and-swap), `auth.ts` (PIN login, sessions, throttling), `catalog.ts` (snapshot reads, first-run seeding, change sets; re-materializes the stock map and drops orphan stock rows), `orders.ts` (public `POST /api/orders`; admin list, manual orders, item edits, status changes that move stock — all through `planStock()`, which nets give-back/take per combination — anonymize, delete), `payments.ts` (admin Pix charge → payment link token; public `GET /api/pay/:token` and receipt upload; admin-only receipt download), `stock.ts` (admin stock read/write, snapshot publishing), `customers.ts` (the owner's customers; link to orders), `resellers.ts` (admin side of the reseller program: applications, resellers, invites, program, kits, settlement), `revenda.ts` (reseller side: invite/contract/PIN, login, her panel, her sales, public showcase), `revendaCore.ts`, `stockPlan.ts` (planStock/takeForLines shared by orders and kits), `push.ts` + `webpush.ts` (Web Push: subscriptions, notices, RFC 8291/8292 with WebCrypto), `mercadopago.ts` (automatic Pix: create, signed webhook, settle), `conflicts.ts`, `media.ts`, `leads.ts`, `live.ts` (`LiveHub` Durable Object), `migrations/` (D1 schema), `test/` (unit + integration).
- `src/data/` — `schema.ts` (zod schemas/types, `SCHEMA_VERSION` 2, `Catalog` = public catalog incl. optional `stock` map and `settings.pix`/`settings.lowStockThreshold`, `CatalogState` = backup with leads), `stock.ts` (stock rules shared by both sides), `orders.ts` (order schemas, statuses/transitions, server pricing `priceOrder`), `report.ts` (sales report, computed in the browser), `seed.ts` (24-product initial catalog; the server seeds D1 from it on its first request), `integrity.ts` (backup migrations, `checkIntegrity`, `validateCatalog`; shared with the Worker), `changes.ts` (change sets: diff/apply/chunk; shared), `storage.ts` (localStorage helpers for per-visitor data + catalog cache + legacy-catalog detection), `catalog.ts` (selectors: prices, badges, variant galleries).
- **Catalog data flow:** `GET /api/catalog` returns a materialized snapshot (ETag `"c<version>"`, 304 on revalidation; `/api/catalog/v/<n>` is immutable and edge-cached). The browser keeps the last snapshot in `eka:catalog-cache:v2` and renders it instantly on return visits; `CatalogGate` holds pages until the first catalog is known (never a flash of "não encontrado"). Admin edits: `save(update)` → `commit` diffs the catalog, uploads new photos (data URLs → `POST /api/admin/media`, content-addressed keys `media/<sha256>.<ext>`), sends one change set with `baseVersion` and an `Idempotency-Key`, and only updates state after the server confirms. The server checks per-entity conflicts (incl. tombstones for deleted items), integrity and photo existence, then commits rows + snapshot in one D1 batch guarded by the catalog version; then the `LiveHub` pushes `{type:"catalog",version}` to every open page.
- **Orders and stock:** the bag's "Finalizar pedido" registers the order (`POST /api/orders`, `Idempotency-Key` per bag content; the server prices it from the snapshot and refuses sold-out/over-stock lines with 409), then shows the number and the "Enviar pedido pelo WhatsApp" link (no Pix at checkout); on a network failure it offers WhatsApp without a number.
- **Manual orders and item edits:** Pedidos → "Novo pedido" (`POST /api/admin/orders`, `Idempotency-Key`; `source: 'manual'`; born "enviado" or "confirmado", the latter takes stock in the same batch) and "Editar peças" (`PUT /api/admin/orders/:id/items { items, stamp }`, only enviado/confirmado; lines already in the order keep the agreed price, new lines take today's; a confirmed order swaps stock atomically; a new total drops `charge` and `pay_token`; history gets `{event: 'itens'}`). The owner may sell hidden pieces (`priceOrder(..., { owner: true })` skips availability and stock checks; the server checks exact stock when the order holds it).
- **Phone notices (Web Push):** `public/sw.js` (root, no caching, no fetch listener) shows `{ title, body, url, tag }`. Configurações → "Avisos no celular" subscribes the device (`/api/admin/push*`, table `push_subscriptions`, max 10 devices, push-service host allow-list). New site orders, receipts and automatic payments notify every device with the order number and amount only; 404/410 erase the device. Needs the `VAPID_PRIVATE_KEY` secret (JWK of an ECDSA P-256 key; the public key is derived from it); without it the section is hidden. iPhone: only from the installed "Painel ÉKA" (iOS 16.4+). Notices open `/admin/pedidos?pedido=<número>`.
- **Automatic Pix (Mercado Pago):** on only when `MP_ACCESS_TOKEN` and `MP_WEBHOOK_SECRET` exist (then a charge no longer needs the static key). The payment page asks the customer's e-mail (Mercado Pago requires it; not stored), creates one payment per charge (`X-Idempotency-Key eka-<charge token>-<seq>`, 24 h, `external_reference <order id>:<charge token>`) and stores `charge.mp`; the page polls every 5 s and has "Já paguei" (`POST /api/pay/:token/pix/check`). `POST /api/webhooks/mercadopago` (no same-Origin guard; `x-signature` HMAC over `id:<data.id>;request-id:<x-request-id>;ts:<ts>;`, 5 min tolerance) fetches the payment from the API and marks the order paid (CAS confirmado → pago, `charge.paidBy`) only when approved, BRL, same order and charge, exact amount. Setup: `docs/vendas/PIX_AUTOMATICO.md`.
- **Installable app:** "Instalar o app" in the store menu and footer, "Instalar o Painel" in the admin menu (`src/components/install/*`, `src/lib/install.ts`, `src/hooks/useInstallPrompt.ts`): native prompt on Android/desktop Chrome, step-by-step guide on iPhone (Safari/Chrome), "open in Safari/Chrome + copy link" in Instagram/Facebook/WhatsApp in-app browsers; "Agora não" hides it for 30 days. `/admin` swaps to `public/admin.webmanifest` ("Painel ÉKA", scope `/admin`) and its icons (`scripts/admin-icons.mjs`).
- **Customers (Painel → Clientes):** table `customers` (WhatsApp unique when present), `orders.customer_id` (+ `order.customerId`). "Novo pedido" picks or creates a customer; a site order can be linked later. When a sale is registered as confirmado (manual) or an order with a linked customer goes to pago, the panel opens "Compra registrada" (items, total, `{garantia}`, `{garantia_ate}`, `{garantia_regras}` = `settings.warrantyTerms`) in her WhatsApp chat — sending needs one tap (the official WhatsApp API is not used). Deleting a customer unlinks her orders; anonymizing an order drops its link.
- **Reseller program (docs/revenda/PLAN.md):** Painel → Revendedoras has Revendedoras · Fichas de cadastro · Programa e contrato. Applications (`leads.status`: nova → analise → aprovada/recusada → efetivada) are effectivated into `resellers` with a one-time first-access link (`/revenda/convite/<token>`, 7 days, hash only) and a showcase `/r/<slug>`. Contract: acceptance in the panel (typed name, version, SHA-256; texts in `contract_versions`) or an external link; a new contract version shows in her panel (`/api/revenda/me` → `contractDue`, `POST /api/revenda/contract`) and her sales are refused until she accepts it. Reseller panel `/revenda` (WhatsApp + 6-digit PIN, cookie `__Host-eka_revenda`, 30 days; installable "ÉKA Revenda"): summary (sold, commission tier progress, accumulated profit, due date), kit, sales (with the customer message + warranty), undo within 24 h, history. Kits (`kits`, one open per reseller) take tracked pieces out of stock (`maleta`) and give back on settlement (`retorno_maleta`); sales (`reseller_sales`) never touch the central stock and are CAS-guarded on the kit stamp. Program in `app_config` key `revenda` (tiers frozen per kit, cycle days, contract); defaults in `src/data/revenda.ts` (25/30/35% from R$ 0/1.000/2.000, 30 days) until Érika confirms. Settlement: sold − commission + missing pieces at full price. Reseller changes ride the live "leads" notice; the owner gets push notices for contract acceptance and reseller sales.
- **Stock entries/exits:** Painel → Estoque "Registrar entrada/saída" (`POST /api/admin/stock/moves`, motives in `src/data/stock.ts`), summary in casa × nas maletas × total and value; an entry on an untracked piece turns stock control on.
- **Photo standardizer:** "Padronizar" on a photo in the product form (`src/admin/products/standardize/*`): on-device background removal with Transformers.js 4.3.2 + BiRefNet lite 512 fp16 (MIT, ~98.5 MB from Hugging Face on first use, then browser cache; revision pinned in `models.ts`), WebGPU or WASM in a worker started from a `blob:` URL (inherits the `/admin` CSP: `'wasm-unsafe-eval'`, Hugging Face hosts in `connect-src`, `worker-src blob:`); ONNX Runtime files are self-hosted in `/assets` (the WebGPU runtime ships gzipped through a plugin in `vite.config.ts`). Composes the piece on the catalog backdrop (`BACKDROP` light map + paper grain measured on the 13 catalog photos, so new photos match the stand-ins), 4:5, ~72% fill, warm contact shadow; "Realce de cor" slider (0–100 %, `enhance.ts`: saturation/vibrance, midtone lift, gentle contrast, light warmth that spares whites) with a half-size live preview, full size rendered on save; the strength she saves becomes the default for her next photos (per device, `eka:standardizer:v1`, default 50 %); before/after, erase/restore brush, keep the original. Nothing of the engine is in the public bundle. Test photos: `assets/test-photos/`; measurement: `node scripts/measure-standardizer.mjs` (`--strength 0,50,100` renders each filter strength); decision and samples: `docs/qa/standardizer/`. Limits: peak memory ~2.5 GB (low-memory phones may fail), thin chains get a slight halo, transparent stones keep the background tint.
- **Message templates:** every WhatsApp text comes from `src/data/messages.ts` (18 types: customer buttons incl. `garantia` and `procura`, the owner's from the admin, and the reseller group; 3–4 built-in variations each, "Clássica" = the original wording). `settings.messages` stores only the owner's changes (active variation, edited built-in texts, her own variations), validated strictly on write; reads fall back to the defaults when it does not validate. Rules: `{variavel}`, optional `[ … ]`, lines whose variables are all empty disappear, values are never altered by the tidy-up. Site: `useMessages()`; admin: Painel → Mensagens (editor with live preview) and "Enviar mensagem" in an order (`OrderMessages.tsx`). Plan: `docs/vendas/MENSAGENS_PLAN.md`.
- **Payment:** in the admin order, "Cobrar por Pix" confirms the order if needed (stock held) and creates `order.charge` (items + frete − desconto) with a secret token (`orders.pay_token`); a new amount issues a new token. The owner copies the ready WhatsApp message (link `/pagamento/<token>` + Pix copia e cola). The payment page (`src/pages/Payment.tsx`, lazy, outside the store layout) shows the summary, QR/copia e cola and takes receipts (PNG/JPEG/WebP/PDF; big images become JPEG in the browser, `src/lib/receipt.ts`; server sniffs magic bytes; ≤ 1.9 MB, 6 per order, D1 `receipts` table). Receipts are personal/financial data: admin-only (`/api/admin/receipts/:id`), erased by anonymize/delete. The admin sees a "Comprovante" badge and accepts with "Pagamento conferido" (→ pago). Brand illustrations: `assets/illustrations/` (generated in ChatGPT) → `npm`-less `node scripts/prepare-illustrations.mjs` → `public/images/illustrations/`. Stock truth is `stock_tracked` + `stock_levels` (a tracked product's missing combination counts as 0); every stock change rewrites the snapshot's `stock` map (capped at 20) and bumps the catalog version in the same guarded batch. Statuses: enviado → confirmado → pago → entregue, or cancelado (`src/data/orders.ts`); entering confirmado/pago/entregue takes tracked items out of stock, leaving gives back exactly `order.stockMoves`. History in `stock_movements`. Orders (personal data) are admin-only; the live channel only says `{"type":"orders"}` to admin sockets.
- `src/store/` — Zustand stores: `catalog` (server catalog, `status`, `version`, async `commit` queue, live connection via `startCatalog()`, `leadsVersion`/`ordersVersion`), `cart`, `checkout` (the order just registered, in memory), `favorites`, `customer`, `ui` (toasts, panels, open-dialog count).
- `src/lib/` — `api` (fetch wrapper, `ApiError` with pt-BR messages), `live` (WebSocket client: heartbeat, backoff, reconnect on focus/online), `pix` (static Pix BR Code + CRC16, key validation), `orders` (order API client), `pin` (PIN policy shared with the Worker), `format` (BRL), `whatsapp` (order message + `wa.me` links), `catalogQuery` (URL-driven filters), `lead` (reseller form schema/mask, shared with the Worker), `search`, `slug`, `assets` (public asset/srcset helpers), `image` (photo pipeline), `csv`.
- `src/components/{ui,layout,product,home,bag}`, `src/pages/*`.
- `src/admin/` (lazy route chunk at `/admin`, opens on Pedidos): `PinGate` (6–8 digit PIN checked by the server), `AdminApp` (session check, returns to the keypad when a request finds the session expired), `AdminShell` (tabs Pedidos · Produtos · Estoque · Relatório · Mensagens · Categorias · Revendedoras · Configurações · Backup, open-order badge, connection banner), `sections/OrdersPage` (status flow, cancel, anonymize, delete), `sections/StockPage` (per-product stock with compare-and-swap, movements), `sections/ReportPage` (periods, KPIs, chart, rankings, stale orders, CSV), `products/` (list, full-screen form with photo manager and variants editor, `productDraft.ts` validation), `sections/` (categories, leads from the API + CSV, settings + Pix + "últimas unidades" threshold + PIN change + checklist, backup: server export, import/restore as change sets, offer for a legacy localStorage catalog), `lib/` (async `save()`, session API, leads hook, contact formatting, downloads, reorder).
- localStorage keys: `eka:catalog-cache:v2` (offline copy of the catalog), `eka:cart:v1`, `eka:favorites:v1`, `eka:customer:v1`. `eka:catalog:v1` is the pre-backend catalog; the admin Backup page offers to download it or send it to the site.

## Backend operations
- **Secrets** (Worker secrets, never in the repo): `PIN_PEPPER` (≥ 32 random chars; keys the PIN and IP hashes; rotating it invalidates the stored PIN) and `ADMIN_INITIAL_PIN` (accepted only until a PIN is stored; the first login stores it). Set with `npx wrangler secret put <NAME>`.
- **Admin access**: PIN of 6–8 digits; 5 attempts per network per 15 min (then 15 min → … → 24 h locks), 50 per hour globally (devices that logged in before are exempt from the global cap). Sessions: `__Host-eka_admin` cookie (HttpOnly, Secure, SameSite=Strict), 14 days idle / 30 days max; changing the PIN ends the other sessions.
- **Locked out or forgot the PIN**: `npx wrangler d1 execute eka-semijoias --remote --command "DELETE FROM throttle"` clears locks; `... --command "DELETE FROM admin_credentials"` makes `ADMIN_INITIAL_PIN` valid again (set a new one with `wrangler secret put` first).
- **Schema changes**: add `worker/migrations/NNNN_name.sql`; `npm run deploy` applies pending migrations before deploying. Never edit an applied migration.
- **Rollback**: `npx wrangler rollback` (code). D1 Time Travel restores the database to a point in time (`npx wrangler d1 time-travel restore`), 7 days on the Free plan, whole database (leads included).
- **Static assets:** `not_found_handling` is `none`; the Worker serves `index.html` for page routes, so a missing `/assets/*` file is a 404 (never HTML cached as immutable JavaScript). `/assets/*` runs the Worker (`serveAsset`): immutable only when the file exists, `no-store` otherwise. Never mark `/assets/*` immutable in `public/_headers` or exclude it from `run_worker_first`: a 404 seen during a deploy rollout was once cached for a year and blanked the site (2026-11-24). The client reloads once on a failed chunk load (`src/lib/chunkReload.ts`). After a deploy, check every new file without a query string (`curl -s -o /dev/null -w '%{http_code}' <site>/assets/<file>`).
- **Optional secrets:** `VAPID_PRIVATE_KEY` (phone notices; generate a P-256 JWK, e.g. the snippet in `docs/vendas/PIX_AUTOMATICO.md`; rotating it requires turning the notices on again on each device) and `MP_ACCESS_TOKEN` + `MP_WEBHOOK_SECRET` (automatic Pix). Local: `.dev.vars` may hold a separate dev VAPID key.
- **Receipts:** `POST /api/pay/:token/receipt` is throttled to 20/hour per network and 300/hour overall. Receipts live in D1 (rows ≤ 2 MB).
- **Orders:** `POST /api/orders` is throttled to 15/hour per network and 300/hour overall; a test order can be deleted in the admin (only while it holds no stock: cancel first). Production test orders must be deleted right after.
- **Free plan limits** that matter: 100k Worker requests/day (static assets are free and unmetered), 10 ms CPU per request, D1 5 GB / 5 M rows read per day. Upgrade (Workers Paid) before traffic nears the request cap or before adding orders/Pix.

## Ground rules
- UI copy in Brazilian Portuguese; code, comments and commits in English.
- Voice: this is the real site, not a demo. No "demonstração/prévia/exemplo/placeholder/ilustrativa/não é segurança/pendente" in the public UI. The brand speaks as itself ("a gente", "nós"); never mention Érika in the third person (her name only on Sobre, in first person). `e2e/public.spec.ts` enforces this on every public route.
- Stack: Vite 8 + React 18 + TypeScript strict + Tailwind v4 (tokens as CSS variables in `src/styles/tokens.css`, mapped with `@theme inline`; custom utilities via `@utility` so responsive variants work) + `createBrowserRouter` with clean paths (`/catalogo`, `/produto/<slug>`, `/admin`; the Worker answers every page route with `index.html`, see `run_worker_first` in `wrangler.jsonc`; old `#/` links are rewritten by `src/legacyHashRedirect.ts`), Vite `base: '/'`. Static files at the root must be listed as `!/<file>` in `run_worker_first` so they skip the Worker.
- Business facts live in `src/config/business.ts` (starting values) and the owner's `loja` section. Never hard-code a fact or claim in a component; public copy belongs in `src/content/defaults.ts` (editable in Painel → Site).
- Design tokens: exact hex values and contrast results in `docs/PLAN.md` §1.1. Rose gold `#B48C78` is never text on light backgrounds; copper `#8A5A45` is the primary/action color. WhatsApp actions use copper, never WhatsApp green.
- Sheets/drawers/modals use the native `<dialog>` wrapper `src/components/ui/Sheet.tsx` (focus trap, Esc, focus return). Toasts portal into the topmost open dialog because modal dialogs make the rest of the page inert.
- Images: seed images are asset stems (`images/products/<name>` → `-480.webp`/`-960.webp`; wide lifestyle shots also `-1440`); uploads are content-addressed server photos (`media/<sha256>.<webp|jpg|png>`, main ≤ 1200 px + 480 px `thumb`), served immutable from `/media/`; data URLs exist only in the admin until the save uploads them. Stand-ins are tracked with `placeholder: true` in data only.
- Never use the reference brand's (Áthama) name, photos or copy.
- Money is integer centavos; format with `formatBRL` (`Intl.NumberFormat('pt-BR', { style: 'currency', currency: 'BRL' })`).
- Storage and API writes must surface errors; never fail silently, never show an unconfirmed save as saved.
- Every server write is validated with the shared zod schemas and `checkIntegrity`; the browser runs the same checks first for instant feedback, but the server is the authority.
- Personal data (leads) only through admin endpoints; never in the public snapshot, logs or WebSocket messages.
- Content the owner replaces herself in the admin before go-live: the Sobre story (Painel → Site → Sobre), real testimonials (Painel → Site → Depoimentos; none are shipped), stand-in photos (Produtos; banners in Site). The privacy policy text (`privacidade` default) mirrors what the system really collects: update the default when a new kind of personal data is added.

## Tools
- `scripts/prepare-images.mjs` (sharp): asset conversion (see Commands). `scripts/shots.mjs` + `scripts/tile.mjs`: ad-hoc screenshot/tiling helpers for visual review.
- `tools/brand/`: palette extraction, recolor, tracing and SVG rendering scripts used to build the logo set (Python with Pillow/NumPy, potrace, Playwright). Not part of the site build.
- `tools/research-capture.js`: the Playwright script that captured the reference screenshots.
